The Machine Learning Lifecycle: Where Engineers Actually Spend Their Time

June 3, 2026 · Practical perspective on the full ML lifecycle

Most ML tutorials focus on model architecture and training. In production, that's maybe 20% of the work. Here's what the full lifecycle looks like — and where your time actually goes.

1. Business Goal Definition (~5-10% of time)

This is where most projects silently fail. Before writing a single line of code, you need to answer:

  • What business metric are we trying to move? Revenue, engagement, cost reduction, user satisfaction?
  • What does "good enough" look like? A 2% improvement in CTR might justify six months of work. A 0.1% improvement might not.
  • Is ML even the right solution? Sometimes a rule-based system or a simple heuristic gets you 80% of the way there.

In practice: You'll spend weeks in meetings with product managers, stakeholders, and domain experts. The deliverable isn't code — it's alignment. You're translating vague business asks ("we want smarter recommendations") into measurable objectives ("increase average order value by 5% within 90 days").

Common time sinks:

  • Stakeholders changing success criteria mid-project
  • Discovering the problem is ill-defined only after you've started
  • Negotiating between what's technically feasible and what's commercially valuable

2. ML Problem Framing (~10-15% of time)

Once you know the business goal, you translate it into an ML problem. This step is deceptively hard.

Key decisions:

  • Task type: Is this classification, regression, ranking, generation, anomaly detection?
  • Label definition: What counts as a "positive" example? A click? A purchase? A 30-second dwell time?
  • Prediction window: Are you predicting what happens in the next hour, day, or month?
  • Offline vs. online: Do you need real-time inference or is batch acceptable?
  • Baseline: What's the simplest model that could work? Always start here.

In practice: You'll prototype quickly, fail fast, and reframe often. A "churn prediction" problem might become a "next-best-action" problem once you realize that predicting churn without a mechanism to act on it is useless.

Common time sinks:

  • Label leakage (your labels accidentally contain future information)
  • Choosing a proxy metric that doesn't correlate with the actual business outcome
  • Overcomplicating the formulation when a simpler one would work

3. Data Processing (~40-50% of time)

This is where you actually live. The meme is true — most of ML engineering is data work.

What this includes:

  • Data discovery: Finding what data exists, who owns it, how to access it
  • Data quality assessment: Missing values, duplicates, drift, inconsistencies, stale pipelines
  • Feature engineering: Transforming raw data into signals the model can use
  • Pipeline construction: Building reproducible, testable ETL/ELT workflows
  • Data validation: Schema checks, distribution monitoring, freshness guarantees
  • Labeling: Managing annotation teams, defining guidelines, measuring inter-annotator agreement

In practice: You'll write more SQL and Spark than PyTorch. You'll discover that the "clean dataset" someone promised you has 30% null values in the key column. You'll spend days tracking down why a feature suddenly shifted — only to find an upstream team changed their logging format without telling anyone.

Common time sinks:

  • Joining data across systems with different keys, timestamps, and granularities
  • Handling PII and compliance (GDPR, data retention policies)
  • Waiting for data backfills
  • Fighting with data infrastructure (Spark OOMs, slow queries, schema evolution)
  • Building feature stores and ensuring training/serving feature parity

The uncomfortable truth: If your data is bad, no model architecture will save you. The best ML engineers I've worked with are exceptional data engineers first.

4. Model Development (~15-20% of time)

This is what everyone thinks ML engineering is. It's important, but it's a smaller slice than you'd expect.

What this includes:

  • Experimentation: Trying architectures, hyperparameters, loss functions
  • Training infrastructure: Distributed training, GPU management, experiment tracking
  • Evaluation: Offline metrics, slice analysis, fairness checks, error analysis
  • Iteration: The feedback loop between evaluation and re-training

In practice: You'll start with a simple baseline (logistic regression, XGBoost) and be surprised how often it's competitive. You'll use experiment tracking tools (MLflow, W&B, internal platforms) religiously. You'll spend more time on evaluation than training — understanding where the model fails matters more than squeezing out another 0.1% on aggregate metrics.

Common time sinks:

  • Debugging silent training bugs (data loading order, label encoding, feature scaling)
  • Hyperparameter tuning that doesn't meaningfully move metrics
  • Reproducing results across environments
  • Managing GPU resources and training queues

What separates production from Kaggle:

  • You care about latency, model size, and inference cost — not just accuracy
  • You need to explain predictions to stakeholders
  • You version everything: data, code, config, model artifacts
  • You think about how the model degrades gracefully, not just how it performs at peak

5. Deployment and Monitoring (~15-20% of time)

Getting a model into production is half the battle. Keeping it healthy is the other half.

Deployment includes:

  • Serving infrastructure: REST APIs, gRPC, batch inference, edge deployment
  • A/B testing: Experiment design, traffic splitting, statistical significance
  • Rollout strategy: Shadow mode, canary releases, gradual ramp-up
  • Integration: Making sure the model's output actually reaches the product

Monitoring includes:

  • Data drift detection: Are inputs shifting away from training distribution?
  • Model performance tracking: Are predictions still accurate in the real world?
  • Alerting: When should you retrain? When should you roll back?
  • Feedback loops: How do you collect ground truth labels from production?

In practice: You'll discover that your model is perfect offline but degrades online because of latency-induced feature staleness. You'll build dashboards that nobody looks at until something breaks. You'll set up retraining pipelines that run on schedules that are either too frequent (waste) or too infrequent (staleness).

Common time sinks:

  • Training/serving skew (features computed differently at training vs. inference time)
  • Model rollback procedures when a new version underperforms
  • Debugging production incidents at 2 AM because a feature pipeline broke
  • Managing model versions across multiple environments (dev, staging, prod)

Key Takeaways

  1. The lifecycle is not linear. You'll loop back constantly. Bad model performance sends you back to data. Production drift sends you back to retraining. Stakeholder feedback sends you back to problem framing.
  2. Data work dominates. If you want to be effective in production ML, invest in your data engineering skills. SQL fluency, pipeline design, and data quality intuition are more valuable day-to-day than knowing the latest architecture.
  3. The "boring" stages have the highest ROI. Getting problem framing right saves months. Solid monitoring prevents production fires. Neither is glamorous.
  4. Production ML is a team sport. You'll work with data engineers, platform engineers, product managers, and domain experts. Communication skills matter as much as technical skills.
  5. Simplicity wins. The model that ships and stays healthy in production beats the clever one that never makes it past a notebook.

The gap between "I trained a model" and "this model reliably drives business value in production" is where ML engineering lives. It's less about algorithms and more about systems thinking, data craftsmanship, and operational discipline.
