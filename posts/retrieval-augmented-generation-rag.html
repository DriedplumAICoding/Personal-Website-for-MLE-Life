Retrieval Augmented Generation (RAG): From First Principles to the 2025 Frontier

Every few months, someone declares RAG dead. “Just use a model with a million-token context window,” they say. And yet, every production LLM system I’ve seen — from enterprise search to customer support bots — still has a retrieval layer at its core. Turns out, shoving your entire knowledge base into a prompt is neither cheap nor reliable.

The RAG pipeline at a glance

At its core, RAG is simple: given a user query, find relevant documents, then feed them to an LLM to generate a grounded answer. The devil is in each of those steps. 

Query → [Query Analysis] → [Retrieval] → [Reranking] → [Generation] → Answer
               ↑                ↑
        [Indexing Pipeline]   [Vector Store / Search Index]

Let’s walk through each stage, starting with how you prepare your data.

1. Indexing: chunking strategies that actually matter

Before you can retrieve anything, you need to break documents into chunks, embed them, and store them. The chunking strategy has an outsized impact on retrieval quality — get this wrong and no amount of fancy reranking will save you.

The classics

  • Fixed-size chunking — split every N tokens with some overlap. Simple, predictable, and often good enough for homogeneous documents.
  • Recursive character splitting — split on paragraph breaks, then sentences, then characters. A hierarchy that tries to preserve semantic boundaries.
  • Semantic chunking — compute embeddings for each sentence, then split where cosine similarity between adjacent sentences drops below a threshold.

What’s new: contextual chunking (2024)

Anthropic’s contextual retrieval approach addresses a fundamental problem: chunks lose context when ripped from their parent document. The idea is elegant — use an LLM to prepend a short contextual summary to each chunk before embedding: 

import anthropic

client = anthropic.Anthropic()

def add_context_to_chunk(document: str, chunk: str) -> str:
    """Prepend document-level context to a chunk before embedding."""
    response = client.messages.create(
        model="claude-sonnet-4-6-20250514",
        max_tokens=200,
        messages=[{
            "role": "user",
            "content": (
                f"<document>\n{document}\n</document>\n"
                f"<chunk>\n{chunk}\n</chunk>\n\n"
                "Give a short (1-2 sentence) context that situates this chunk "
                "within the overall document. Only output the context, nothing else."
            )
        }]
    )
    context = response.content[0].text
    return f"{context}\n\n{chunk}"

A chunk that originally says “Revenue increased 15% year-over-year” becomes “This is from Acme Corp’s Q3 2024 earnings report, discussing financial performance. Revenue increased 15% year-over-year.” The embedding now captures both the fact and its provenance.

Anthropic reported this reduced retrieval failure rates by 49% when combined with BM25 hybrid search. That’s not a marginal improvement.

Late chunking (2024)

Jina AI introduced late chunking: instead of chunking first and embedding each chunk independently, you embed the entire document through a long-context embedding model, then split the resulting token embeddings into chunks. Each chunk’s representation is informed by the full document context.

This sidesteps the information loss problem entirely — each chunk embedding “knows” what the rest of the document says, because it was computed with full bidirectional attention. The tradeoff: you need a long-context embedding model, and indexing is more expensive. But retrieval quality improves significantly for documents where context is crucial (legal contracts, technical manuals, research papers).

2. Embedding & vector storage

Choosing an embedding model

The MTEB leaderboard changes monthly, but some principles hold:

  • Task-specific models outperform general ones. If your retrieval is code search, use a code-trained model. If it’s multilingual, pick one trained on parallel corpora.
  • Dimensionality is a knob, not a fixed choice. Matryoshka Representation Learning (MRL) models let you truncate embeddings to smaller dimensions with graceful degradation — use 256d for filtering and 1024d for final ranking.
  • Don’t sleep on instruction-prefixed models. Models like E5-mistral-7b-instruct accept task-specific instructions and significantly outperform non-instructed variants.

Binary quantization: the 2024 efficiency trick

Full float32 embeddings are expensive to store and search. Binary quantization converts each dimension to a single bit (positive → 1, negative → 0), reducing storage by 32x and enabling Hamming distance search on CPUs. 

import numpy as np

def binary_quantize(embeddings: np.ndarray) -> np.ndarray:
    """Convert float embeddings to packed binary vectors."""
    binary = (embeddings > 0).astype(np.uint8)
    return np.packbits(binary, axis=1)

def hamming_distance(a: np.ndarray, b: np.ndarray) -> int:
    """Fast hamming distance between packed binary vectors."""
    xor = np.bitwise_xor(a, b)
    return sum(bin(byte).count('1') for byte in xor)

The typical pattern: use binary vectors for coarse candidate retrieval (top-1000), then rescore with full-precision vectors for the final top-k. You get 95%+ of the recall at a fraction of the cost.

3. Retrieval: hybrid search is no longer optional

Why embedding-only search fails

Pure vector search has blind spots:

  • Exact matches — searching for error code ERR_0x4F2A won’t match semantically
  • Negation — “companies that are NOT profitable” and “companies that are profitable” have nearly identical embeddings
  • Rare entities — names, acronyms, and domain jargon that the embedding model hasn’t seen enough of

Hybrid = BM25 + dense retrieval + reciprocal rank fusion

The 2024 consensus: always combine lexical (BM25/SPLADE) with dense retrieval, then fuse results.

from dataclasses import dataclass

@dataclass
class SearchResult:
    doc_id: str
    score: float

def reciprocal_rank_fusion(
    result_lists: list[list[SearchResult]],
    k: int = 60
) -> list[tuple[str, float]]:
    """Fuse multiple ranked lists using RRF. k=60 is the standard constant."""
    scores: dict[str, float] = {}
    for results in result_lists:
        for rank, result in enumerate(results, start=1):
            scores[result.doc_id] = scores.get(result.doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

# Usage: fuse BM25 and vector search results
bm25_results = bm25_search(query, top_k=100)
vector_results = vector_search(query_embedding, top_k=100)
fused = reciprocal_rank_fusion([bm25_results, vector_results])

Why RRF works so well: it’s rank-based, not score-based, so you don’t need to calibrate scores across fundamentally different retrieval methods. A document that appears in the top-10 of both BM25 and vector search gets boosted; a document that only one method finds still gets included.

SPLADE: learned sparse retrieval

SPLADE learns sparse representations that bridge lexical and semantic search. It expands queries with related terms (like “jaguar” → “jaguar car automobile vehicle”) while remaining sparse enough for inverted index search. Think of it as BM25 with learned query expansion. Many vector databases (Qdrant, Vespa, Weaviate) now support SPLADE natively alongside dense vectors.

4. Reranking: the accuracy/latency tradeoff

Initial retrieval (BM25 + dense) casts a wide net. Reranking narrows it with a more expensive model.

Cross-encoders

A cross-encoder takes (query, document) as a single input and outputs a relevance score. Unlike bi-encoders, it can model fine-grained token interactions between query and document — but it’s O(n) per query-document pair, so you only run it on your top-k candidates.

ColBERT: the best of both worlds

ColBERT’s “late interaction” architecture computes query and document embeddings independently (like a bi-encoder) but scores them with a token-level MaxSim operation: 

Score(q, d) = Σ𝑖 maxⱼ (q𝑖 · dⱼ)

Each query token finds its best-matching document token, and scores are summed. This gives cross-encoder-level quality at bi-encoder-level latency for retrieval.

Reranking in 2025: LLM-based rerankers

A newer pattern: use an LLM itself as a reranker. Cohere’s Rerank v3, Jina Reranker v2, and open models fine-tuned for ranking (RankLLaMA, RankZephyr) outperform traditional cross-encoders on many benchmarks. The key insight: LLMs can do listwise reranking — rank all candidates at once rather than scoring each independently — which captures inter-document relevance signals.

5. Query analysis: helping the retriever help you

Raw user queries are often vague, ambiguous, or poorly structured for retrieval. Query analysis transforms them before hitting the index.

Multi-query expansion

Generate multiple reformulations of the original query, retrieve for each, then merge results:

def generate_multi_queries(query: str, n: int = 3) -> list[str]:
    """Generate diverse query reformulations for broader recall."""
    response = client.messages.create(
        model="claude-sonnet-4-6-20250514",
        max_tokens=300,
        messages=[{
            "role": "user",
            "content": (
                f"Generate {n} different search queries that would help answer "
                f"this question from different angles:\n\n{query}\n\n"
                f"Return only the queries, one per line."
            )
        }]
    )
    return response.content[0].text.strip().split("\n")

HyDE: hypothetical document embeddings

Instead of embedding the query directly, ask an LLM to generate a hypothetical answer, then embed that. The generated text is closer in embedding space to real relevant documents than a short query would be. This works surprisingly well for questions where the query phrasing is far from how the answer is expressed in the corpus (e.g., “why is the sky blue” vs. a physics textbook paragraph about Rayleigh scattering).

Query routing (2024–2025)

Modern RAG systems don’t send every query to the same pipeline. A query router classifies intent and dispatches:

  • Factual lookup → RAG pipeline
  • Conversational/chitchat → LLM directly (no retrieval needed)
  • Structured data question → text-to-SQL
  • Multi-hop reasoning → decompose into sub-queries

This is the bridge to agentic RAG — the system decides how to answer, not just retrieves.

6. Generation: beyond “stuff it in the prompt”

Prompt construction

A production RAG prompt has layers:

[System Prompt]        → persona, constraints, output format
[Retrieved Context]    → ranked chunks, with source attribution
[Conversation History] → prior turns for multi-turn coherence
[User Query]           → the actual question
[Instructions]         → "cite sources", "say I don't know if unsure"

Order matters. Placing retrieved context before the query (rather than after) consistently improves faithfulness — the model “reads” the evidence before seeing what it needs to answer.

Citation & grounding

The gap between “the model said something” and “the model said something backed by the retrieved documents” is where hallucinations live. Techniques that help:

  1. Inline citations — instruct the model to cite [Source 1], [Source 2] alongside claims.
  2. Sentence-level grounding — post-process each generated sentence, checking if it’s entailed by any retrieved chunk (using an NLI model or LLM judge).
  3. Structured generation — use constrained decoding to force the model to produce JSON with claim/source pairs.

Long-context models vs. RAG: not either/or

Models with 128K–1M token context windows don’t eliminate the need for RAG. They change the architecture:

  • Retrieval still handles scale. You can’t put 10M documents in context. Retrieval narrows the haystack.
  • Long context handles depth. Once you’ve retrieved 20 relevant documents, a long-context model can reason over all of them simultaneously rather than being limited to 3–4 chunks.
  • The “needle in a haystack” problem is real. Models degrade on information buried in the middle of long contexts. Retrieval + smart ordering mitigates this.

The 2025 pattern: retrieve broadly, then let long-context models synthesize across many documents.

7. Evaluation: the RAG triad and beyond

You can’t improve what you can’t measure. RAG evaluation is notoriously tricky because you’re evaluating a pipeline, not a single model.

The RAG triad

Metric Measures How
Context Relevance Did retrieval find the right stuff? Judge: “Is this chunk relevant to the query?”
Groundedness Is the answer supported by retrieved context? Judge: “Is this claim supported by the chunks?”
Answer Relevance Does the answer address the query? Judge: “Does this answer address what was asked?”

LLM-as-judge: practical tips

def judge_groundedness(answer: str, context: str) -> dict:
    """Use an LLM to evaluate if the answer is grounded in context."""
    response = client.messages.create(
        model="claude-sonnet-4-6-20250514",
        max_tokens=500,
        messages=[{
            "role": "user",
            "content": (
                "You are evaluating whether an AI answer is grounded in the "
                "provided context.\n\n"
                f"<context>\n{context}\n</context>\n\n"
                f"<answer>\n{answer}\n</answer>\n\n"
                "For each sentence in the answer, determine if it is:\n"
                "- SUPPORTED: directly supported by the context\n"
                "- PARTIALLY_SUPPORTED: partially supported\n"
                "- NOT_SUPPORTED: not found in the context at all\n\n"
                "Return JSON with 'sentences' (list of {text, verdict}) "
                "and 'groundedness_score' (fraction of supported sentences)."
            )
        }]
    )
    return response.content[0].text

Watch out for:

  • Self-preference bias — models prefer outputs from their own family. Use a different model as judge than as generator when possible.
  • Position bias — judges favor the first option in A/B comparisons. Randomize order.
  • Verbosity bias — longer answers often get higher scores regardless of quality. Normalize for length.

Retrieval-specific metrics

Don’t just evaluate the final answer — evaluate retrieval independently:

  • Recall@k — of all relevant docs, what fraction did we retrieve in top-k?
  • MRR (Mean Reciprocal Rank) — how high is the first relevant result?
  • nDCG@k — accounts for graded relevance and position discount.

Build a golden evaluation set (50–100 query/relevant-doc pairs minimum) and track these over time. This is the single highest-leverage thing you can do for RAG quality.

8. Agentic RAG: the 2025 paradigm shift

This is where things get interesting. Traditional RAG is a fixed pipeline: retrieve → generate. Agentic RAG makes the system adaptive — an LLM agent decides when to retrieve, what to retrieve, and whether the results are good enough.

The core loop

User Query
    ↓
Agent (LLM with tools)
    ├―― Tool: search_documents(query)
    ├―― Tool: search_web(query)
    ├―― Tool: query_database(sql)
    ├―― Tool: ask_clarification(question)
    └―― Tool: generate_answer(context)
    ↓
[Agent evaluates results]
    ├―― Sufficient → Generate final answer
    └―― Insufficient → Reformulate and search again

Self-RAG (2024)

The SELF-RAG paper introduced a model that generates special “reflection tokens” to decide:

  1. [Retrieve] — do I need to retrieve? (Yes/No)
  2. [IsRel] — is this retrieved passage relevant? (Relevant/Irrelevant)
  3. [IsSup] — is my generation supported by the passage? (Fully/Partially/No)
  4. [IsUse] — is this response useful? (5-point scale)

The model learns to self-correct by critiquing its own retrieval and generation at each step. This collapses the external evaluator into the generation model itself.

Corrective RAG (CRAG, 2024)

CRAG adds a lightweight evaluator that assesses retrieved documents and takes corrective actions:

  • Correct — documents are relevant → proceed with generation
  • Ambiguous — partially relevant → refine query and re-retrieve
  • Incorrect — documents are irrelevant → fall back to web search or refuse to answer

Multi-agent RAG

For complex questions requiring information from multiple domains or sources, spawn specialized retrieval agents: 

import asyncio

# Conceptual multi-agent RAG architecture
agents = {
    "technical_docs": RAGAgent(index="engineering_docs", expertise="technical"),
    "financial_data": RAGAgent(index="sec_filings", expertise="financial"),
    "customer_feedback": RAGAgent(index="support_tickets", expertise="customer"),
}

async def answer_complex_query(query: str):
    plan = orchestrator.plan(query)  # Which agents are needed?
    results = await asyncio.gather(*[
        agents[agent_name].retrieve_and_summarize(sub_query)
        for agent_name, sub_query in plan.items()
    ])
    return synthesizer.combine(query, results)

This is where RAG meets multi-agent systems. The orchestrator handles planning, the specialized agents handle domain-specific retrieval, and a synthesizer combines everything into a coherent answer.

9. GraphRAG: structure-aware retrieval

Microsoft’s GraphRAG (2024) addresses a fundamental limitation of chunk-based RAG: it can’t answer questions that require synthesizing information across many documents. “What are the main themes in this dataset?” requires global understanding — no single chunk contains the answer.

How it works

  1. Extract entities and relationships from all documents using an LLM, building a knowledge graph.
  2. Detect communities in the graph using algorithms like Leiden clustering.
  3. Generate community summaries — LLM-written summaries of each cluster of related entities.
  4. At query time, retrieve relevant community summaries (for global questions) or traverse the graph (for local questions).

When to use GraphRAG vs. vanilla RAG

Scenario Best Approach
“What does document X say about Y?” Vanilla RAG (local lookup)
“What are the major trends across all reports?” GraphRAG (global synthesis)
“How are entities A and B related?” GraphRAG (relationship traversal)
“Find the paragraph that defines term Z” Vanilla RAG (exact retrieval)

The cost: GraphRAG indexing is 10–100x more expensive (every chunk gets an LLM extraction pass). It’s worth it for corpora where inter-document relationships matter — research papers, legal documents, enterprise knowledge bases — but overkill for FAQ-style retrieval.

10. Production considerations

Building a RAG demo takes an afternoon. Making it production-ready takes months. Here’s what matters.

What to log (everything)

@dataclass
class RAGTrace:
    request_id: str
    timestamp: float
    # Input
    raw_query: str
    rewritten_queries: list[str]
    # Retrieval
    retrieved_chunks: list[dict]  # id, score, text, metadata
    reranked_chunks: list[dict]
    retrieval_latency_ms: float
    # Generation
    assembled_prompt: str
    generated_response: str
    generation_latency_ms: float
    token_usage: dict  # input_tokens, output_tokens
    # Quality signals
    user_feedback: str | None  # thumbs up/down, if collected

Log every intermediate step. When quality degrades, you need to pinpoint whether retrieval or generation failed — and you can’t do that from the final answer alone.

Metrics to monitor

System health:

  • P50/P95/P99 latency (end-to-end, retrieval, generation separately)
  • Retrieval null rate (queries returning zero results)
  • Token usage and cost per query

Quality signals:

  • User feedback rate and sentiment
  • Groundedness score (sampled, via LLM judge on a fraction of traffic)
  • Citation accuracy (do cited sources actually support the claims?)

Safety:

  • Prompt injection detection rate
  • PII leakage in responses
  • Refusal rate (is the system refusing too often or not enough?)

The feedback loop

The best RAG systems have a tight iteration loop:

  1. Identify failures via user feedback and automated quality checks
  2. Categorize into retrieval failures (right answer exists but wasn’t retrieved) vs. generation failures (right context retrieved but answer is wrong/hallucinated)
  3. Fix retrieval failures by improving chunking, adding query expansion, or tuning the index
  4. Fix generation failures by improving prompts, adding guardrails, or fine-tuning

This diagnosis step — retrieval vs. generation — is the most important mental model for debugging RAG systems.

Where RAG is heading

A few trends worth watching:

  1. RAG + fine-tuning convergence. RAFT (Retrieval Augmented Fine-Tuning) trains models to be better consumers of retrieved context — learning to ignore distractor documents and reason from relevant ones.
  2. Multimodal RAG. Retrieving and reasoning over images, tables, and diagrams alongside text. ColPali (2024) embeds document page images directly, bypassing OCR entirely.
  3. Cache-augmented generation. With prompt caching (prefix caching), you can pre-load a large knowledge base into the model’s KV cache and serve queries against it with minimal per-query retrieval latency.
  4. Memory-augmented systems. Personal RAG that maintains a persistent, evolving knowledge base from your interactions — more like an extension of the model’s memory than a traditional search system.

The through-line: RAG is evolving from a static pipeline into a dynamic, adaptive system that decides how to access and use knowledge. The fundamentals — chunking, embedding, retrieval, generation — remain load-bearing. But the orchestration layer is where the innovation is happening.

Key takeaways

  • Hybrid search (BM25 + dense + RRF) is table stakes. Don’t ship embedding-only retrieval.
  • Chunking strategy > model choice for retrieval quality. Invest time here.
  • Contextual chunking and late chunking solve the “chunk without context” problem that plagues naive RAG.
  • Evaluate retrieval and generation separately. Build a golden set. Track metrics over time.
  • Agentic RAG is the direction of travel — systems that decide when and how to retrieve.
  • GraphRAG unlocks global/synthesis questions that chunk-based RAG fundamentally can’t answer.
  • Log everything. You can’t improve what you can’t observe.
